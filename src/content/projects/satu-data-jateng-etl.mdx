## The Problem Context

Migrating tabular data from a legacy repository to a new centralized portal, Satu Data Jateng, presents significant challenges. Legacy government datasets often exhibit inconsistent naming conventions (for example, "Data Padi Jawa Tengah" versus "Jawa Tengah Data Padi"), spacing errors, unstandardized region codes, duplicate entries, and unstandardized schemas. 

If this data is migrated without careful consideration, using a standard API script, the new portal could quickly become cluttered with duplicates, incorrectly formatted columns, and 422 Unprocessable Entity errors. 

**The Solution:** The dual-mode ETL (Extract, Transform, Load) pipeline is an advanced solution that boosts data processing with resilience, human validation, and stateful migration. It functions in both batch and real-time streaming modes, suitable for various data loads. Its resilience ensures continuous data availability during interruptions or system failures, which is crucial for reliable operations. The human-in-the-loop validation engages data professionals, improving data accuracy and quality. Stateful migration tracks data context and status, preserving relationships and original states essential for accurate reporting and analytics.

## System Architecture

To ensure data integrity, the pipeline strictly separates the auditing phase from the execution phase, using CSV files as a hard "Data Contract" between the two processes.

```text
┌──────────────────────────────────────────────────────────────────────────┐
│                           main.py (CLI)                                  │
│                    --mode audit | --mode migrate                         │
└─────────────┬─────────────────────────────────┬──────────────────────────┘
              │                                 │
              ▼                                 ▼
┌─────────────────────────┐      ┌──────────────────────────────┐
│   MigrationPipeline     │      │   MigrationLoadPipeline      │
│   (Mode: Audit)         │      │   (Mode: Migrate)            │
│                         │      │                              │
│  1. Extract via API     │  ──► │  1. Read Verified CSVs       │
│  2. Fuzzy Deduplication │      │  2. Column Normalization     │
│  3. Data Preprocessing  │      │  3. Stateful POST to Target  │
│  4. Hybrid Reporting    │      │  4. Progress Tracking        │
└─────────────────────────┘      └──────────────────────────────┘
```

### Architectural Decisions

1. **Dual-Mode Execution:** Separating `--mode audit` and `--mode migrate` forces a human-in-the-loop validation step. Managers can review the generated Executive Excel Reports and raw CSVs before any data touches the production API.
2. **CSV as a Data Contract:** For a one-time, large-scale migration, standing up an intermediate SQL database introduces unnecessary overhead. CSVs serve as a perfectly immutable, auditable handover format between the Audit and Migrate phases.

## Deployment & Operations

The system was built for operational reliability, backed by an extensive `pytest` suite ensuring transformation logic remains stable.

The deployment workflow strictly follows a 4-step execution strategy:
1. **AUDIT (Automated):** Pulls legacy data, flags anomalies, generates hybrid Excel/CSV reports.
2. **REVIEW (Manual):** Data stewards verify flagged datasets and adjust `column_mapping.json` (if needed).
3. **MIGRATE (Automated):** The stateful pipeline pushes `Load_Ready_*.csv` payloads to the new infrastructure.
4. **MONITOR (Manual):** Evaluates `migration_progress.csv`. If partial failures exist, step 3 is simply re-run.

## Technical Innovations

1. **NLP Fuzzy Deduplication & Auto-Mapping:** Legacy systems often lack strict primary keys across identical datasets. To prevent migrating duplicates, the `catalog_assessor.py` module implements Natural Language Processing via the `thefuzz` library. 
	* It uses `token_sort_ratio` to detect dataset titles that are identical in meaning but ordered differently.
	* To prevent false positives (e.g., mistaking two distinct datasets due to a 1-character typo), it utilizes **bidirectional fuzzy row fingerprinting** to verify the actual underlying data.

2. **Dynamic Column Normalization:** A major bottleneck during API migration is structural rejection (HTTP 422). The `ColumnNormalizer` dynamically reads from a centralized `column_mapping.json`. It renames non-standard legacy columns to match the strict schema requirements of the new Satu Data API before the payload is built.

3. **Stateful Batch Migration:** Network drops during a massive data migration are inevitable. The `MigrationProgressTracker` ensures the script can be killed and restarted without risk of duplicating data.
